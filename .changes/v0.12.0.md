## v0.12.0 - 2026-08-30
### Added
* A target that runs a container can state its own `command`, so the container's entry point travels with the version instead of staying behind in Terraform. A command names a path inside the image, which means an image whose layout moves and a command that has not are a job that will not start — and until now those were two writes in two tools with no ordering between them: Terraform applies a command change immediately on a job, where nothing carries traffic and the next execution simply picks it up, while the image only arrives with the next release. Declared here the two land in one write. It sits on a target and never on a service, because a service whose targets all took the same command would be describing one job several times over, and the whole command line goes in it: the declaration is the entry point the way `env` is the environment, so arguments the container carried separately are dropped with it — Cloud Run appends args to command, and a leftover pair would start the container on a line nobody wrote. Omitting it keeps what the target already has, which is what every config written before this goes on doing, so nothing has to change to stay on Terraform's. A command that moved while the version did not now counts as a change on its own, and the plan says `command changed` rather than `environment changed`, which was the only reason left that an unchanged version could carry. All five container types take it — `cloud-run`, `cloud-run-job`, `container-app`, `container-app-job` and `ecs` — and it is refused on `lambda` and `function-app`, where the host is handed a package and owns the entry point itself. The platforms disagree on what to call the two fields: Cloud Run and Container Apps follow Kubernetes, where `command` is the entry point and `args` follows it, while ECS follows Docker, where `entryPoint` is the entry point and `command` follows. You write the whole line either way, and on ECS it goes to `entryPoint` with `command` cleared — writing it into the field that merely shares the name would leave the real entry point in place and append to it. On ECS the entry point also moves out of the task-definition fingerprint's catch-all, so a command the deploy config owns is no longer reported as the base task definition having moved underneath it.
