## v0.10.0 - 2026-08-27
### Added
* A Cloud Run revision now carries the release it is running as an `evolve-deploy/version` annotation, so `deploy`, `diff`, `traffic` and `rollback` can name the version on each side of a blue-green service. The image cannot answer that question here — Cloud Run stores it as the digest the tag resolved to — and the service's own template, which does keep the tag, belongs to whichever revision was created last: after a failed deploy that is the one that was abandoned, which is exactly why a blue-green plan reads the serving revision instead. An annotation rather than a label, because a label value may hold neither a dot nor a capital and `v1.2.3` is a tag people use. It is written on staging and read back on the next run, so a side deployed before this exists still reports its version from the image tag where there is one.
### Changed
* A version the platform keeps no record of now reads `(unknown)` rather than `(none)`, and nothing refuses because of it. The two were the same word before, which was wrong in both directions: `(none)` is the honest answer for a traffic entry that has no tag, and the wrong one for a release that is certainly serving but cannot be named. More than cosmetic in one place — `rollback` compares the version the idle side holds across every target and refuses a set that does not agree, and an unreadable version counted as a value there rather than as the absence of one. Two Cloud Run services, one redeployed since the version started being stamped on the revision and one not, would have had a correct rollback refused for the single reason nobody can act on. An unknown version is now a gap in what can be displayed and never a reason to stop a deploy or a rollback that is otherwise right.
* A blue-green switch on Cloud Run now takes the tag off the side that stops serving, so that side is retired by the platform instead of being paid for until the next release. A tag is an address — `blue---service.run.app` answers whether or not any traffic is split that way — so an idle side that kept its tag was never retired, and on a service whose template carries `scaling.min_instance_count` it went on holding that floor indefinitely: one extra instance per service, permanently, since each release leaves a new idle revision holding one. The revision a rollback needs is recorded in an `evolve-deploy/rollback` annotation on the service instead. It has to live there rather than on the revision, because revisions are immutable and the revision that must be named is the one that stopped serving a moment ago; a write masked to the service's annotations touches no template, so it creates no revision of its own. The note is written before the traffic moves, so the failure that can be left behind is a note naming a side that is still serving, which is a rollback to where you already are and is ignored on the next read. Nothing is deleted and `rollback` is unaffected in what it can reach — it re-tags the recorded revision and moves the traffic to it, a cold start as before. A service deployed before this exists still has both tags in its traffic block, and those are still read in preference to the note, so no release has to go first. What is gone is the idle side's own URL: there is no longer an address to curl the previous version on before deciding to go back to it. This also makes two things the tool already printed true rather than nearly true — the `(scaled to zero)` on the rollback line, and the reasoning the `keep_warm` refusal gives.
### Fixed
* A Cloud Run service whose Terraform bootstrap writes the traffic split and the tag as two separate blocks — `traffic { percent = 100 }` next to `traffic { tag = "blue" }`, both following the latest revision — is no longer refused. Both entries resolve to one revision and Cloud Run serves them as a single tagged entry at 100%, which is why the console shows blue carrying everything while the tool read the spec block, found the percentage on an entry with no tag, and asked for the bootstrap that was already there. The tag is now read off the entry beside it when the two aim at the same revision, and the first release pins the pair back to the one-line form the tool writes. It stays a refusal when both tags claim the serving revision, since then there is no side to deploy away from, and when the tag is pinned to a revision while the percentage follows whatever is newest — a rule and a reference are not the same target even when they happen to agree today.
* A blue-green release on Cloud Run no longer fails at staging with `must be a container image path in the form [hostname/]repo-path[:tag and/or @digest]`. A Cloud Run revision records the image as the digest the tag resolved to and keeps no note of what was written, so the reference read back from a serving revision is `repo@sha256:9ca1640…` even where Terraform declared `repo:8618aae`. Splitting that took the colon in `sha256:` for the tag separator, which made the repository `repo@sha256`, the running version the digest hex — the 64-character hash that showed up in plans as the version being rolled back to — and the image written for the next revision `repo@sha256:8618aae`, which is neither a tag nor a digest. It only surfaced on the blue-green path, because that one reads the serving revision rather than the service template, and only once staging was already under way. A digest is now understood wherever a reference is read, and replaced by the tag being deployed rather than concatenated with it.
