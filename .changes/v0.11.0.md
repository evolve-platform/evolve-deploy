## v0.11.0 - 2026-08-27
### Added
* `evolve-deploy prune <config>` removes Cloud Run revisions that nothing needs any more. Cloud Run keeps every revision it has ever been given and nothing there expires, so a service deployed twice a day accumulates them until it meets a quota — one test environment here was holding 811 revisions of a single service, of which two described anything running. Four things survive a sweep, read off the platform at the moment it runs rather than from any release: the revision serving traffic and anything else the traffic block names, the revision a LATEST entry resolves to, the revision recorded as the side to roll back to, and anything younger than the retention window. That third one is why this is a command and not a shell loop — a blue-green switch takes the tag off the side it retires, so from the outside the rollback target is indistinguishable from the hundreds behind it, and the obvious rule of "delete what has no tag and no traffic" would throw away the only thing `rollback` can reach. Cloud Run refusing to delete a revision that serves traffic is the second lock on that door. The retention window is 90 days and hardcoded for now; it will become a setting in the deploy config, and until then a younger revision is kept whatever else is true of it. Every revision looked at is reported with the reason it was kept, so `--dry-run` is worth reading before the first sweep of a long-lived service — which is also slow, because each removal is waited for. Deleting a revision cannot be undone. Container Apps and ECS keep no comparable stack of revisions to sweep, and the command says so rather than pretending to have swept.
### Fixed
* A blue-green Cloud Run release no longer stages the running container over what Terraform declares. Only the image and the environment are read from the serving revision — the two fields a deploy owns and Terraform is told to ignore, so the service template is not current for either. Everything else on the container is Terraform's and now comes from the service, the same as scaling, service account and VPC access one level up. Taking the whole container meant ports, probes, cpu and memory travelled with it: an apply that changed a probe created a revision carrying no traffic, and the next release put the old values straight back on the side it staged. Found as a liveness probe that kept polling the port the service had been moved off, which failed every check and had each instance killed under it.
